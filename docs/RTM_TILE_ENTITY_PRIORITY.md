# RTM Tile Entity Performance Priority — Second Pass

**Review date:** 2026-09-30  
**Mode:** source review and engineering prioritization only; no code changes, benchmark, packet capture, or in-game run.

The [tile entity audit](RTM_TILE_ENTITY_AUDIT.md) is the evidence census. This document interprets its findings against actual call paths, inheritance, likely instance count, and engineering cost. The [performance architecture audit](RTM_PERFORMANCE_AUDIT.md) describes the already migrated machine runtime, energy and fluid networks, and dirty synchronization. Ratings below are qualitative expectations, not measured speedups. “Prevalence” is an expectation from block registration and use, not a world count. A rare tile can still be expensive when it broadcasts to every client or scans every loaded entity.

## Decision rules and source corrections

* **Frequency and cost are separate.** A cheap callback on many blocks and a costly ray trace on one powered turret need different evidence. Server tick means a loaded tile receives 20 callbacks per nominal second; elapsed real time falls with TPS. Render work is per visible frame. An update method containing `new` is not proof that allocation happens every loaded tick.
* **Current machine infrastructure matters.** `TileEntityLoadedBase` has 242 concrete descendants and owns lifecycle/runtime binding but no `updateEntity()` loop. `TileEntityMachineBase` has 147 concrete descendants and makes `updateEntity()` abstract; it does not add a generic per-tick scan. The 186 runtime-covered members of the separate 205-class machine census already use `MachineRuntime` strategies; active one-tick simulation and fallback COARSE_5/20/100 checks have documented reasons. `TileEntityCableBaseNT`, `TileEntityPipeBaseNT`, and proxy bases disable tile ticking. Do not add a second scheduler or count every machine callback as a remaining idle scan. See [current runtime status](RTM_PERFORMANCE_AUDIT.md#current-machine-runtime-status--2026-09-27) and [residual cadence](RTM_PERFORMANCE_AUDIT.md#remaining-one-tick-work-after-the-cadence-pass).
* **Storage and reactor bases have different cost.** `TileEntityCrateBase` owns inventory behavior for eight descendants and has no base update loop; simple crates can still receive a no-op callback. `TileEntityRBMKBase` covers 14 reactor-column descendants and schedules active simulation through `MachineRuntime`; its heat/physics cost is conditional work, not generic idle polling. Its active cadence cannot be slowed without changing simulation. [crate base](../src/main/java/com/hbm/tileentity/machine/storage/TileEntityCrateBase.java), [RBMK base](../src/main/java/com/hbm/tileentity/machine/rbmk/TileEntityRBMKBase.java#L133).
* **Two entries in the first audit's packet table overstate idle *wire* traffic.** `TileEntityRadioTorchCounter` and `TileEntityTurretBaseNT` call `TileEntityMachineBase.networkPack()`, which compares the new NBT with the last packet and normally sends an unchanged baseline only when world time is divisible by 20. They still **build/compare NBT every server tick**; active turret fields can genuinely change every tick. The static `INBTPacketReceiver.networkPack()` used by radio base/logic and Drone Requester has no such suppression. The door, launcher, radar-screen, and CIWS direct sends are unconditional. Source: [machine packet helper](../src/main/java/com/hbm/tileentity/TileEntityMachineBase.java#L250), [generic NBT helper](../src/main/java/com/hbm/tileentity/INBTPacketReceiver.java#L14).
* **The two turret bases have different breadth.** The bomb `TileEntityTurretBase` has only one active concrete subclass, CIWS. Its list copy and LOS ordering are serious *per powered CIWS*, not an inherited defect across all NT turrets. The NT base has 13 concrete descendants in the audit; 11 reach its update body, while Arty and HIMARS duplicate the connection/snapshot pattern in their overrides. Thus all 13 can benefit from a family migration, but a base-only edit misses two. [CIWS base](../src/main/java/com/hbm/tileentity/bomb/TileEntityTurretBase.java#L43), [NT base](../src/main/java/com/hbm/tileentity/turret/TileEntityTurretBaseNT.java#L165), [tile mappings](../src/main/java/com/hbm/tileentity/TileMappings.java#L281).
* **The RequestNetwork timer is a real global hot-path bug when drone nodes exist.** `ServerTickEvent.START` calls `updateEntries()` once per server tick. Its `timer < 0` branch cannot be reached after `timer = 20`; every call traverses active worlds, chunks, and nodes, checking wall-clock leases. Cost is near zero when its map is empty. Its 2,000 ms lease must still expire with bounded latency. [caller](../src/main/java/com/hbm/main/ModEventHandler.java#L1721), [timer](../src/main/java/com/hbm/tileentity/network/RequestNetwork.java#L18).
* **Dummy tiles are a potential instance multiplier.** `TileEntityDummy.updateEntity()` reads the saved controller block every server tick, even while the structure is unchanged. `DummyOldBase` and the Blast/Vault dummy blocks create this TE; a multiblock can contain many cells. The number loaded in real worlds is unknown. Replacing this probe needs correct teardown when a controller disappears, chunk-safe ownership and a bounded fallback for changes outside the controller's own code. [dummy update](../src/main/java/com/hbm/tileentity/machine/TileEntityDummy.java#L15), [dummy block base](../src/main/java/com/hbm/blocks/machine/DummyOldBase.java#L25).
* **Registered does not mean common.** The radio torch blocks, doors, launchers, radar screen, CIWS, and drone tiles have block creation and tile mappings. Their prevalence labels below reflect likely use: simple signal devices are plausible common placements; giant launch and door structures are rare. No deployment statistics were available. [block definitions](../src/main/java/com/hbm/blocks/ModBlocks.java), [tile mappings](../src/main/java/com/hbm/tileentity/TileMappings.java).

## A. Immediate high-ROI fixes

1. **Repair the RequestNetwork expiry cadence.** This is a small, high-confidence removal of a global traversal on 19 of 20 nominal ticks when nodes exist. Keep lease expiry and world cleanup semantics.
2. **Constrain CIWS's gauge sync.** Its `sendToAll()` reaches clients unrelated to the turret every server tick, including stationary unpowered periods. Preserve smooth client rotation while spinning and initial state for newly watching clients. Its connection descriptor can be cached separately with low risk.
3. **Skip obviously ineligible launcher power scans.** Launch Table checks up to 81 blocks per idle server tick, Compact Launcher nine. A cheap already-known empty/uncharged guard can avoid those world queries; a full `canLaunch()` call may itself inspect missile/designator/fuel, so measure or inspect before moving it outside the loop. [launch code](../src/main/java/com/hbm/tileentity/bomb/TileEntityLaunchTable.java#L178), [compact code](../src/main/java/com/hbm/tileentity/bomb/TileEntityCompactLauncher.java#L169).
4. **Read only Vault Door's orientation plane.** The current path scans both 30-position planes while unlocked, then uses one; this saves up to 30 redstone queries per loaded tick per door with little state risk. Its rarity limits aggregate payoff.
5. **Avoid the Counter's unconditional inventory snapshot when no channel/filter is active.** Its adjacent tile lookup and `ItemStack[]` copy run every server tick even with three empty channels. A channel eligibility guard removes the entire scan for an unconfigured counter. A configured counter still needs its live inventory semantics.
6. **Cache CIWS's fixed underside port descriptor.** This removes a one-element array and `DirPos` allocation on every server tick. It is a small win to bundle with gauge work.

## B. Shared infrastructure with high potential

The best shared change is an **explicit dirty sync contract for tiles outside the migrated machine path**, applied family by family. The existing `TileEntityMachineBase.networkPackNTIfDirty()` and `MachineRuntime` patterns already establish the policy: mutation marks client state dirty, and a baseline repairs late viewers. Radio Base/Logic, Drone Requester, doors, launchers, and Radar Screen each need coverage for their own state transitions; none should be switched on solely because it subclasses a base. This can remove packet construction and all downstream network work on unchanged ticks. Table B details the affected set and dependency order.

Start that contract with **Radio Torch Base and Logic**. Sender and Receiver inherit the base serializer, and Logic repeats the same every-tick configuration send. Tracking control/mapping mutations is moderately involved, yet it removes NBT construction, serialization, recipient lookup, bandwidth, and client decoding together for a plausible common device family.

Next, move stable connection geometry and subscriptions in **the NT turret family** to lifecycle/topology invalidation with a bounded compatibility renewal. Eleven descendants use the base update and two artillery descendants duplicate it. This is a real family multiplier, but orientation, dummy metadata, power-network attachment, unload/rebind, and optional compatibility need careful preservation. The existing `UniNodespace`/`MachineRuntime` ownership should be reused.

The most ambitious shared opportunity is **request/drone graph invalidation**. `TileEntityRequestNetwork` currently revisits a 5-by-5 chunk map and re-ray-traces known paths once per second for each node; Drone Dock searches an 11-by-11 chunk region and rebuilds request/offer lists once per second only while holding a drone. Stable graph caching could remove chunk lookups, allocations, and two ray traces per known path, but block occlusion, leases, priority, path fairness, and chunk lifetime make this a profiling-led architecture project. Do not conflate it with the already event-driven power/fluid conductor graphs.

**Dummy controller liveness** is another shared, profiling-led candidate. Every loaded dummy makes a block lookup each tick, and one structure may own many dummy cells. An owner-driven invalidation path could remove thousands of simple world queries in dummy-heavy worlds, but the saved target currently lacks an ownership token and cross-chunk teardown semantics are fragile. Repair the ownership model as part of any wake/sleep change; a timer-only throttle would delay orphan cleanup.

## C. Local and secondary optimizations

The Blast Door's 499 redundant dummy-operation *attempts* per full open/close cycle are certain, but doors change state infrequently; make threshold events one-shot for correctness and moderate transition CPU savings. The legacy CIWS can reject out-of-range candidates before LOS and avoid copying the whole loaded entity list; its cost is high during powered AI but only one rare concrete class inherits that base. Launcher packet and fluid/item refresh fixes are worthwhile within a launcher family pass, yet expected loaded-instance counts are low. Radar Screen's packet is unconditional, but its entry list is cleared after send and repopulated by `TileEntityMachineRadarNT`; optimize from that producer/consumer timing rather than suppressing packets blindly. Selected door/turret render bounds warrant capture before narrowing them.

## D. Findings outside the performance backlog

The 78 empty concrete updates, nine inherited empty updates, and 72 default/no-HBM updates provide mostly dispatch overhead. Even with 143 ordinary callback-eligible classes, no expensive body is inherited from `TileEntityLoadedBase` or `TileEntityMachineBase`; prioritize only after an instance-count and profiler result. The 66 infinite AABBs and 171 256-block overrides are lexical counts, not 237 independently expensive renderers. The 27 hot-allocation candidates include active, once-per-second, and conditional paths; only verified hot allocations appear in Table A. Unused `sysTime`, duplicate directional code, NBT normalization, dummy *teardown* ownership, global `safeBreak` flags, Blast Door lock precedence, and recursive door propagation deserve correctness/robustness work, but those events alone are not performance wins. The dummy's **separate per-tick liveness probe** is a performance candidate. A door-chain traversal can be costly on unusually large connected components; its ordinary frequency is transition-only.

## Profiling required before reprioritization

1. **Loaded population and packet fan-out:** count loaded Sender/Receiver/Logic/Counter, Requester, launcher, door, Radar Screen, CIWS, and NT turret instances by dimension; measure each packet ID's sends/s, recipients/send, encoded bytes/s, and client decode time. This could reorder rows 2–13.
2. **Request network scale:** sample nonempty `activeWaypoints` worlds/chunks/nodes, `updateEntries()` calls/tick and mean/p95 time, expired nodes/pass, request-node count, known paths/node, two-way raytraces/s, and dock path-search time. Compare an active drone installation with an empty map.
3. **Turret target cost:** for powered CIWS, record loaded entity count, eligible missile count, candidate count after cheap distance rejection, LOS raytraces/tick, mean/p95 scan time, and `toArray()` allocations/s on server and client. Do not equate all loaded entities with raytraces: `isInSight()` rejects noneligible types before tracing.
4. **Dummy multiplier:** count loaded dummy tiles per world and per controller type, `TileEntityDummy.updateEntity()` calls/tick, mean/p95 `getBlock` time, observed chunk accesses, orphan removals, and controller unload/replacement events. A few dummy block types can still mean many ticking cells.
5. **Machine residuals:** from current runtime diagnostics, count loaded instances by machine family, active vs idle scheduled callbacks, COARSE_5/20/100 visits, and mean/p95 callback time; correlate fluid push scans, demand queries, dormant skips, and positive-demand work via `/ntmpowerstats`. Keep original producer phases and rate boundaries.
6. **Rendering:** capture visible TESR counts and per-class render calls/frame with and without door/turret broad bounds; record frame time, draw calls, and actual model/effect extents across camera angles. Do not narrow geometry from the AABB count alone.
7. **Radar and launcher clients:** packet payload bytes and changes/s for screen entries, multipart missile state, and scalar buffer; observe packet order at a fresh chunk watcher and during launch or radar scan. A steady state rate without payload changes is the optimization target.
8. **Configured Counter/RTTY networks:** adjacent inventory slot counts, Counter allocations/s, sender comparator queries/tick, polling-mode share, and actual RTTY channel changes/s. These distinguish idle simplifications from externally dynamic behavior.

## Final choice summary

**Top 10 performance per effort:** (1) RequestNetwork reaper cadence, (2) Radio Base dirty config sync, (3) Radio Logic dirty config sync, (4) CIWS idle/global gauge sync, (5) ineligible launcher scan guard, (6) Vault orientation-only scan, (7) Counter inactive snapshot guard, (8) empty multipart suppression, (9) launcher scalar dirty sync, (10) door heartbeat suppression.

**Top 5 systemic/shared changes:** explicit dirty sync policy for non-machine tiles; NT turret connection invalidation; NT turret prepack dirty state; dummy controller liveness/ownership invalidation; request/drone graph invalidation. Radio-family mutation tracking is the best first implementation of the sync policy. The last two require profiling and proof that every relevant world change can invalidate the cached state.

**Top 5 profiling gates:** loaded tile and packet fan-out distribution; loaded dummy cells and controller lookup cost; RequestNetwork node/path scale; powered CIWS candidate/LOS cost; runtime machine residual callback cost. TESR visibility remains a required separate render measurement.

**Top 5 primarily correctness/cleanup findings:** dummy ownership/destructive teardown; Blast Door locked-redstone precedence; deep recursive door chains; leaking global `safeBreak` suppression; malformed door state/NBT and dead `sysTime` cleanup.

**Single best first change:** fix the RequestNetwork expiry timer. It is the clearest one-place removal of recurring graph work, with a direct server-tick caller and low implementation risk, whenever drone nodes exist.

**Best first shared infrastructure change:** radio-family configuration dirty sync, using the existing machine dirty-sync policy and preserving watcher recovery. It establishes a reusable contract without replacing `MachineRuntime` or the conductor networks.

**Highest-potential, highest-risk change:** replacing the per-tick `TileEntityDummy` master probe with owner-driven liveness, if profiling confirms a large dummy population. One multiblock creates multiple dummy cells, so this could remove a broad set of recurring world lookups. It requires durable ownership, safe removal when controllers are broken or replaced, and correct behavior across chunk unload/reload. If dummy counts are low, request/drone graph invalidation becomes the stronger high-risk candidate.
